# 实战教训全记录（2026-11-18 全量归档 1023 篇实测）

为什么管线长这样——每条设计背后都有一次真实翻车。接入新来源前先读这页。

## 1. 列表接口死了，别在尸体上浪费时间

2026-07-30 微信关闭公众号后台「跨号文章列表」能力（appmsgpublish / appmsg action=list_ex）。
三个开源项目（wechat-article-exporter、wechat-download-api、we-mp-rss）同日在**第一页零结果**时复现
`ret=200013 freq control`。它不是限频：
- 等 24 小时无效（实测从 06:47 卡到 15:00 仍是 200013）
- 换 UA、加 X-Requested-With、换 Referer、换 fakeid 全部无效
- `searchbiz`（搜号）和单篇 `/s/` 正文**依然正常**——「搜索成功、列表失败」的分裂现象是它的指纹

结论：看到 200013 直接切客户端凭据通道，不要做任何「等待重试」的尝试。
`profile_ext`（home/getmsg/getmasssendmsg）只带 `__biz` 返回 `no session`——列表必须带 uin/key/pass_ticket。

## 2. 微信 Mac 桌面端抓包：系统代理是死路

微信 Mac 4.x **完全不跟随 macOS 系统代理**（同机的 Chrome、UURemote 都走，唯独微信直连）。
Chromium 式 `--proxy-server` 启动参数也无效（webview 不是标准 Chromium 传参）。

唯一可行：`/etc/hosts` 把 `mp.weixin.qq.com` → 127.0.0.1，本机记录器收明文 80（微信对 mp 走 80）+
443 TLS（须用 mitmproxy CA **签发 SAN 为 mp.weixin.qq.com 的叶子证书**——直接把 CA 证书端出去会被
客户端以「签发者名不符」拒掉）。抓到带 `key=` 的 URL 后立刻提取、立刻还原 hosts + 删 CA。

抓凭据**不需要上游返回成功**——只要请求发出来，URL 里就有全套凭据。所以劫持期间微信显示「未知错误」
不影响捕获。

## 3. 验证页长得不像验证页

微信安全验证页 `secitptpage/verify.html` 由 JS 渲染，**页面里没有「环境异常」「验证」等文字**
（实测 17KB，可见文本只有 Video/Like/Wow 按钮文案）。识别它只能靠 `secitptpage/verify` 或
`PAGE_MID` 字符串。

配套教训：本地 API 对抓不到正文的文章返回兜底文案「无法获取文章内容。可能原因：文章被删除、
访问受限或**需要验证**」——其中的「验证」二字曾让脚本把**已删除文章**误判成限频，每 10 分钟重试
同一篇，卡死队列 40 分钟。修复：失败必先直连诊断一次页面，按内容分类：
- `此内容因违规无法查看`/`该内容已被发布者删除`（32KB 页）→ 永久失效，跳过
- `secitptpage/verify` → 整队暂停 15 分钟（实测 14 分钟冷却），然后原篇继续
- 其他 → 软限流退避

## 4. 验证页是累计配额，不是可避免的

公开文章页抓取每 ~100 篇触发一次验证（15 分钟冷却）。节奏参数（8s 间隔、随机抖动）只能减少
触发频率，不能消除。正确的工程姿势是**让暂停自愈**：整队 sleep 后接着跑，一晚跑完 1172 篇
（含 3 次验证暂停约 45 分钟）。

反面教训：把间隔从 5s 提到 20/min 全局限频「提速」，结果 36 篇后就开始返无正文页——那个判断
本身就是误诊（真凶是单篇删除文），真正的限流是验证页形态。

## 5. 广告卡判定：内容说话，不要猜位置

微信在次条位插入短剧/商品推广卡（`mp-common-cpsad`，零文字）。判定规则演进：
- ❌ `idx=2` 位置猜：2024-04 的「【原创】自发觉醒」是正常次条（1563 字正文）——位置与广告无因果
- ❌ 加 `custom_select_card` 标记：泛类标记，正文文章也有，误伤 45/93（一度把 79 篇正文 MD 当广告删了）
- ✅ 4 个精确标记（`mp-common-cpsad`/`data-adtype=`/`new_cps_iframe`/`data-pluginname="mpcps"`）
  **或** 去标签文字 <10 字

删除类操作的教训：先在 raw 层判定、输出清单，再动 MD；一切清洗脚本必须幂等 + 备份可还原。

## 6. 引流尾块：用「（完）」做边界，别做内容匹配

作者引流尾巴高度模板化（404 获取指引 → 个人网站 → 微博 → 公众号矩阵 → 觅圈二维码），但匹配
这些文案做内容清理又脆又费。实测 **970/977 篇正文以「（完）/（未完待续）」收尾**，其后全是引流
——一行边界符胜过十条正则。例外处理：
- 无结束符的：从「404文章获取」「个人网站：」行截断
- 荐书文（正文本身就是推广）：识别为「原价+元/套」形态后**不动**
- 作者笔误「完）」缺半括号：截断逻辑按行首匹配不受影响

## 7. 队列尾部饥饿：索引顺序 vs 重启语义

articles.jsonl 按「从新到旧」追加，最老文章在**文件尾**。每次进程中断重启都从头跑
（raw 断点跳过已抓的），于是老文章永远差一点没轮到——某轮排查时 122 篇 2023-11~2024-04 的
文章直连完全正常却从未被抓过。修复：让单轮跑完全队列（验证页暂停是进程内 sleep，不中断），
中断后重跑自然会推进到尾部。**验收时必须核对「未抓篇数 = 失效数」，差值就是尾部饥饿。**

## 8. 标题去重是陷阱：同名不同文

「周先生的茶馆四代目」与知识库 JM 系列（另一个号/文集）有 14 个相同标题——抽「情绪勒索」
比对正文：线上讲「卖弄悲情/野某」，JM507 讲「家人刻薄」。**完全不同的两篇文章**。常见词标题
（胜负已定、本末倒置、人心所向）碰撞率极高。任何跨库去重必须比正文或比 sn/mid+idx，绝不比标题。

## 9. 环境碎片化：解释器与依赖

本机四个 Python 各管一摊：`/usr/bin/python3`(3.9) 有 playwright+fitz+pdfplumber；
API venv(3.12) 有 markdownify/bs4/curl_cffi；homebrew python 缺 _tkinter；
WorkBuddy 注入的 sitecustomize 会把 mkdir 伪报 EEXIST。管线脚本用错解释器的症状是
`No module named 'markdownify'`——数据没坏，换对解释器重跑即可（raw 断点在，不重抓）。
涉及沙箱注入时统一 `env -u PYTHONPATH`。

## 11. 增量重跑：机械判重兜不住"已经归档"

个人站（zlsdcg.com）2026-11-23 做增量重跑时暴露的三类"看似该入库、其实早就在库里"的假阳性：

1. **纯图片/空正文文章**——正文为空，正文哈希判重完全无从下手，昨天的判定是"新增"，
   重跑会生成 `_wp<ID>` 副本或撞上"禁止覆盖"。
2. **知识库副本被脱敏改写**——发布后做了姓名占位替换，正文哈希不再相等，
   看着像"新文章"，其实是同一篇（ID 55：源站"喝喝"vs 发布稿"呵呵"，只差两字）。
3. **来源链接相同**——同一篇在站内换了发布日期/图片地址后重发，
   只看站内标题去重会误判成"较新版本"（7915 vs 7227）。

**解法**：机械哈希判重之外，加一条**身份锚点**判定——同一 `wordpress_id` 或同一
`source` 链接已在知识库 → 判重复，不再发布。锚点要从知识库 MD 的 frontmatter 读，
不要靠正文相似度猜。

**推论**：这条规则依赖知识库现状，所以 `finalize_review.py` **不是幂等的**——
发布后单独重跑它，会把刚发布的文章改判为重复，与 manifest/验收记录脱节。
要重跑就整链重跑；确需重跑判定，先从 `history/<日期>/review_decisions.json` 恢复发布时状态。

**连带教训**：验收脚本里写死的源站文章总数（2674）会让站点每新增一篇就失败；
数量应从 `fetch_report.json` 的 `fetched_total` 读。

## 12. 微信 link 不是稳定身份：sn 每轮都变（2026-11-23 增量重跑实测）

一次增量同步暴露了一整类问题，起因只有一个：**link 里带运行期参数**。

`https://mp.weixin.qq.com/s?__biz=..&mid=2247492660&idx=1&sn=819f75cf..&chksm=..`
里的 `sn`/`chksm`/`key` 每次抓取都不同，**同一篇文章的 link 字符串每轮都变**。
凡是"跨轮要认得出同一篇"的地方用了整条 link，就会连锁出错：

| 位置 | 用 link 的后果 | 正确做法 |
|---|---|---|
| 索引去重 | 索引里堆重复记录（实测多出 50 条，1172→1232） | 按 `mid+idx` |
| raw 断点 | 存量文章被整轮重抓（实测多抓 18 篇，还撞软限流退避） | 按 `mid+idx` |
| 失败/广告台账匹配 | 永久失效的 21 篇每轮重试，退避到跑不完 | 按 `mid+idx` |

**连带发现**：
- 之前用 link 做键的 raw 断点，等于每轮把全库文章重抓一遍——第一版增量跑挂了 30 分钟，
  根因就在这里。修好后队列从 31+ 篇降到正好 10 篇真新增。
- 索引重复还会让 `state.json` 的 total_articles 虚高，对账等式全线错位。
- 对账脚本不能拿"目录里 MD 总数"去套公众号管线的等式：`公众号直采/` 现在有
  **两条管线**（公众号 + zlsdcg 个人站）共 2702 篇，必须按 frontmatter `source` 分开数。

**解释器纪律**：正文/渲染阶段要用 API venv（有 markdownify/bs4），PDF 用系统 python3。
用错解释器时**正文其实抓成功了**（raw 已落盘），只是渲染阶段全量报错——
看到"渲染失败 xxx：No module named 'markdownify'"要认得出这是解释器问题，不是抓取失败。

**广告判定的新形态**：短剧广告卡的 4 个标记匹配不上、正文又长的**带货软广**
（引导加微信/领白皮书/限时公开）会漏判。已按语义剔除并记账，**没有擅自加文本特征规则**
（误伤风险），判过的广告不再渲染，删掉也不会复活。

## 13. 作者引流尾块还有第二种形态：连配图一起切（2026-11-23）

短剧广告卡之外的引流，正文末尾还有一段作者自带的推广：

```
其他经典的梗还有很多，下次有空再聊。

**更多交流，请关注小红圈（孤苑白首二十年已经完本…）**   ← 引流段
![](_attachments/3706506fbdf202be47e5.jpg)                ← 配图（与正文无关）
```

**判据：引流段连同它后面的配图都不属于正文**，配图往往只是二维码/广告图，
留着就是污染正文。此前两条管线的截断规则都只认「（完）/404文章获取/个人网站：」，
漏掉这一形态——个人站管线存量里带这种尾块的有 775 篇（涉及 830 张配图）。

**修法**：锚点补「更多交流 + 芥末圈/小红圈/孤苑白首」（同一行内），
命中即从该行截断，后面内容（含配图）一并去掉。存量用
`project-zhou/scripts/zlsdcg_backfill_trim.py` 回填（复用管线同一套规则，先备份），
再清掉变成孤儿的配图。

**连带教训（规则版本化）**：`trim_promo_tail.py` 用 `trim_state.json`（mtime+size）
跳过未变更的 MD——**规则改了也必须重判**，否则旧文件被跳过、新规则不生效。
状态里必须存 `RULE_VERSION`，版本不一致就作废旧状态、重新全扫。

**另一条**：公众号直采目录是两条管线共用的，公众号管线的 `trim_promo_tail.py`
与渲染**只处理 `source=mp.weixin.qq.com` 的 MD**，个人站管线（`source=zlsdcg.com`）的文件
不碰——否则一条管线的清洗会改掉另一条管线的归档。
